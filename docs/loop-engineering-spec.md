# Loop Engineering Spec — 循环工程(编码智能体自主循环)

> 状态:设计定稿,待实施(2026-08-19)
> 定位:把用户不在线的时间变成工程时间——一个不需要盯着、不会把事情搞砸、还会自己找活干的"夜班工程师"
> 关联:docs/pane-system-spec.md(右栏改动/预览页卡承担结果呈现)、现有调度器(办公自动化)、审批体系、偏好预设机制

## 0. 用户故事(一切设计的出发点)

**故事 A · 睡前挂机**
> 晚上十一点,小张给项目挂了三个任务:测试修复、lint 清债、依赖升级。设了预算"到明早 7 点,最多 60 万 token"。早上打开 hiq,晨报在等他:"发现并处理了 17 个问题:修复 9 个测试失败、清掉 23 个 lint 警告、升级 2 个依赖(1 个回滚)。4 处高危变更请你裁决。"点开"改动"页卡,变更按任务分组、每个都带验证状态。他花 20 分钟裁决,合并,收工。

**故事 B · 白天并行**
> 小李在主会话写新功能,同时开了一个 L2 循环"补齐 utils/ 的单测覆盖率到 80%"。循环每轮写完测试会弹审批,他顺手批一下;不批,循环就暂停等他——不打断主思路,也不越权。

**故事 C · 只读巡检(第一次使用)**
> 新用户第一次不敢放手。他只开 L1 巡检:agent 扫全仓库,生成一份问题报告(测试缺口、技术债热点、可疑模式),零写入、零风险。看完报告,他决定升级到 L2 试试。

从这三个故事提炼的产品标准:**敢睡(安全)、有得看(报告)、会自己找活(探索驱动)、能叫停(控制)**。

## 1. 核心概念

### 1.1 循环 = 五段闭环

```
   ┌─→ [传感器] 巡检:跑验收命令,扫描问题源,生成/更新问题队列
   │      ↓
   │   [决策] 挑当前最值得的问题(优先级×风险×预算);队列空且连续 N 轮无新问题 → 停机(完成)
   │      ↓
   │   [执行] 一轮 agent 工作流(改代码/写测试/升级依赖…)
   │      ↓
   │   [验证] 跑验收+回归;不通过 → git 回滚本轮,记录失败原因,同问题重试≤2 次后拉黑
   │      ↓
   └── [记账] 更新进度/预算消耗;预算尽或熔断条件触发 → 停机(中止)
```

**目标驱动 vs 探索驱动**:用户可选。目标驱动="把这几个测试修绿"(队列由用户播种);探索驱动="持续提升该仓库质量"(队列由传感器生成)。默认探索驱动——这是"像人一样不断发现问题"的实现。

### 1.2 预算与停机条件(不是"轮数")

用户配置的是**预算**与**停机条件**,而非固定轮数:

| 项 | 默认 | 说明 |
|---|---|---|
| 时间窗 | 手动停止 | 可设"23:00-07:00" |
| token 预算 | 60 万 | 超出即停 |
| 最大轮次 | 30 | 兜底 |
| 停机-完成 | 队列空 + 连续 2 轮无新问题 | 探索模式的自然终点 |
| 停机-熔断 | 连续 3 轮无进展 / 连续 3 轮回滚 | 防原地打转、防越改越糟 |
| 问题重试 | 同一问题 ≤2 次 | 两次失败拉黑并写入晨报 |

### 1.3 自治分级(信任阶梯)

| 级别 | 名称 | 写权限 | 审批 | 适用 |
|---|---|---|---|---|
| L1 | 巡检官 | 无(只读+报告) | — | 首次使用/陌生仓库 |
| L2 | 白班工人 | 有 | 每轮结束弹审批(复用现有 ApprovalModal) | 白天并行 |
| L3 | 夜班工程师 | 有 | 隔夜免审,但:强制独立 git 分支 + 命令白名单 + 高危工具(bash 写、网络)默认拒绝 | 睡前挂机 |

升级需要用户显式操作,且 L3 首次开启弹一次"信任确认"(说明边界与回滚保障)。

## 2. 用户界面规格

### 2.1 入口

侧栏底部,"编码偏好"下方,同款 `cowork-sidebar__item` 按钮:**♾ 循环工程**。循环运行中按钮亮主题色 + 小转角指示;点击打开 LoopPanel(复用 PreferencePanel 的全屏面板形态)。

### 2.2 LoopPanel 布局(主区域)

```
┌───────────────────────────────────────────────────────────────┐
│ 循环工程                                    [总开关 ●———○] [紧急停止]│
├──────────────┬────────────────────────────────────────────────┤
│ 左栏 260px    │ 右侧配置/状态区                                    │
│              │                                                    │
│ ▶ 预置案例    │ 【未运行时 = 配置态】                                │
│  ○ 测试修复   │   目标描述      [textarea]                          │
│  ○ 债务清扫   │   验收命令      [mono input, 如 npm test]           │
│  ○ 覆盖率爬坡 │   探索驱动      [开关:传感器自动发现新问题]            │
│  ○ 依赖升级   │   自治级别      [L1巡检|L2审批|L3隔夜] segmented      │
│  ○ 文档追补   │   预算          时间窗/__ token/__ 轮               │

│   预设机制)   │   第 12/30 轮 · 预算已用 43%                        │
│              │   传感器:✓ 全绿 → 等待下一轮(5m)                     │
│ ▶ 任务队列    │   问题队列:  3 待处理 · 2 重试 · 1 拉黑               │
│  (睡前挂多个  │   本轮:正在修复 utils/date.ts 时区测试 …              │
│   任务的排队  │   [进度时间线:每轮一行,绿✓/红↺回滚/灰跳过]            │
│   列表+拖序)  │   [暂停] [紧急停止]                                 │
│              │                                                    │
└──────────────┴────────────────────────────────────────────────┘
```

要点:
- 配置态/状态态同一区域切换,左侧案例与队列常驻;
- 每轮在时间线可展开:改了什么(文件列表)、验证输出摘要、为何回滚;
- 紧急停止**常驻右上角红色**,与总开关分离(开关=计划性停止,急停=立即杀当前轮)。

### 2.3 晨报(睡醒第一眼)

循环停止(完成/中止/到点)后,LoopPanel 顶部与消息流各出现一份**晨报卡**:

```
☽ 夜班报告 · 23:00 → 07:00 · 预算用 71%
做了什么   测试 +9 修复 12 跳过 0 | lint 清除 23 残留 4 | 依赖升级 2 回滚 1
变更       37 文件,+812/−240 —— [在改动页卡查看分组 diff]
验证       npm test 43/43 ✅  ·  回归 2 次(均已回滚)
需你裁决   ⚠ 3 项:改了公共 API 签名 / 删除了"看似无用"的导出 / 升级了 major 依赖
被拉黑     auth 重连测试(2 次修复失败,原因:需要真实凭证)
建议下一步 补 utils/queue 覆盖率;auth 拉黑项需人工方案
           [逐项审阅] [一键合并已验证变更]
```

- "需你裁决"项点击直达对应 diff(改动页卡定位);
- "一键合并"只合并**通过验证且非高危**的变更,高危项必须逐项。

### 2.4 与现有界面的联动

- 运行中:树里该会话行转圈(已有机制)+ LoopPanel 状态态;
- 每轮 turn 结束:改动页卡蓝点(已有 `changedDirty`);
- 起 dev server 类验收:预览页卡自动弹(已有 URL 探测);
- L2 审批:复用 ApprovalModal,文案标注"循环第 N 轮";
- 紧急停止:全局快捷键 `Ctrl+Shift+\`(与 netdev 急停同款先例)。

## 3. 预置案例目录(内置,可复制改造)

| 案例 | 传感器 | 验收 | 级别建议 | 说明 |
|---|---|---|---|---|
| 测试修复循环 | `npm test`(失败列表) | 同命令全绿 | L2/L3 | 红→绿,失败即问题 |
| 债务清扫 | `npm run lint` / tsc 警告 | 零警告 | L2/L3 | 按优先级清,越清越少 |
| 覆盖率爬坡 | coverage 报告未覆盖分支 | 覆盖率 ≥ N% | L2 | 每轮挑一个分支写测试 |
| 依赖升级循环 | outdated 列表 | 每个升级后测试全绿 | L3 | 逐个升,major 保守 |
| 文档追补 | 公共 API 无注释扫描 | 扫描为空 | L1/L2 | 只加注释,低风险 |
| 性能预算 | benchmark 对比基线 | 达预算线 | L2/L3 | 优化→测→循环 |
| 只读巡检 | 全部传感器 | —(只出报告) | L1 | 首次使用推荐 |

案例 = `{名称, 描述, 传感器命令, 验收命令, 探索开关, 级别建议, 预算建议, goal 模板, 白名单命令}`——存储与"偏好预设"同机制(前后端各一份,`internal/memory/presets.go` 同款)。

## 4. 数据模型(前端视角)

```ts
interface LoopConfig {
  id: string;
  name: string;
  goalTemplate: string;          // 目标描述(用户可编辑)
  sensorCommand?: string;        // 巡检命令(探索驱动)
  verifyCommand: string;         // 验收命令
  exploratory: boolean;          // 探索驱动
  autonomy: "L1" | "L2" | "L3";
  budget: { until?: string; maxTokens?: number; maxRounds: number };
  schedule?: { at?: string; window?: [string, string] };
  commandAllowlist?: string[];
}

interface LoopRun {
  id: string; tabId: string; configId: string;
  state: "running" | "paused" | "done" | "aborted" | "failed";
  round: number;
  budgetUsed: { tokens: number; rounds: number };
  problemQueue: ProblemItem[];
  timeline: RoundRecord[];
}

interface ProblemItem { id: string; source: string; summary: string; priority: number; retries: number; blacklisted?: boolean; }
interface RoundRecord { round: number; problem?: string; changedFiles: string[]; verify: "pass" | "fail-rolled-back" | "skipped"; note?: string; }
interface MorningReport { runId: string; summary: {...}; reviewItems: ReviewItem[]; blacklisted: ProblemItem[]; suggestions: string[]; }
```

## 5. 执行引擎(后端边界,尽量薄)

- **循环体**:每轮 = 一次普通会话提交(结构化提示词:传感器输出 + 问题 + 验收 + 输出契约),智能体用现有 bash 工具改/跑——**不发明新执行原语**;
- **调度**:复用办公自动化的调度器(定时/时间窗),MVP 先做"手动开始 + 时间窗到点自停",二期接定时启动;
- **验证与回滚**:轮末由 Go 侧跑 verifyCommand(RunShellForTab 同通道),失败执行 `git checkout -- .`(L3 独立分支上更安全);token 统计复用 usage 事件;
- **新桥接方法(全部很薄)**:`LoopStart(config)` / `LoopStop(runId)` / `LoopPause` / `LoopStatus() → LoopRun` / 事件 `loop_round`(每轮记账)、`loop_report`(晨报);
- **白名单**:L3 下 bash 命令前缀匹配白名单(config.commandAllowlist + 内置安全集 git/npm/node/python/测试器),拒绝即跳过并记账。

## 6. 安全与信任(隔夜场景的生死线)

1. **恶化防护**:每轮验证不过即回滚——一晚最坏结果是"白跑",不是"改烂";
2. **三重预算**:时间/token/轮次任一触顶即停;
3. **熔断**:连续 3 轮无进展或连续 3 轮回滚 → 停机并写明原因;
4. **L3 强制**:独立 git 分支 + 白名单 + 高危工具默认拒;首次开启弹信任确认;
5. **可审计**:每轮的提示词、diff、验证输出全部落盘(run 目录),可回放;
6. **紧急停止**:全局生效,杀当前轮、不回滚已完成且验证过的轮(保守保留现场)。

## 7. 分期与验收

**MVP(一期,先立骨架)**
- LoopPanel(配置态+状态态)、5+ 预置案例、任务队列(串行多任务)、单轮自循环(提示词工程)、每轮验证+回滚、预算(轮次/token)、熔断、L1/L2(L3 档位可先置灰)、晨报(简版:汇总+裁决清单+合并按钮)、紧急停止;
- 验收:挂"测试修复"过夜场景 demo——次日能出晨报,diff 分组可审,回滚轮在时间线可见。

**二期**
- 定时启动/时间窗(调度器接入)、传感器扩展(coverage/todo/git 热点)、loop_round 事件驱动树/页卡联动打磨、晨报进消息流卡片、循环历史(多次 run 对比)。

**三期**
- L3 隔夜档全量(白名单编辑器、信任确认流)、案例市场(分享/导入)、团队看板(多仓库多循环总览)。

## 8. 边界与不做

- 不绕过现有审批/工具权限体系——循环是"会话的模式",不是新权限主体;
- 不做隐式后台写(所有写入都在会话消息流可见);
- 不与办公自动化合并 UI(复用其调度内核,界面各自独立)。
